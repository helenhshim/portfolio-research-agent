# V2 latency investigation

2026-10-12 · D76 · Local preview only; no deployment or release.

## Observed failure

Helen reports a research deadline while testing. The latest local server trace shows a completed first provider request at 5,901ms, followed by one executed tool and a second provider request cancelled after 114,095ms. The whole-turn code deadline is 120,000ms. The second request had no received-response timing or usage under the previous nonstreaming adapter. This locates the wait at provider synthesis; it does not distinguish network/queue waiting from reasoning or text generation. Default logs do not capture the question or tool arguments, so the tool cannot be identified retrospectively.

There is no runtime SEC retrieval: the controller prepares the frozen report pair locally. The initial context already contains all 504 approved paragraphs (71,068 JSON characters) and all 55 prepared facts. A whole-prior-report reread could resend 34,985 characters already supplied. That duplication is proven in the request construction, not proven to be the sole cause of the timeout.

## Changes

- Prompt `v2-public-research-2` explicitly identifies the complete supplied evidence, discourages rereading already supplied material, and targets a concise brief of at most four hundred authored words while preserving counterevidence, uncertainty and exact quotes.
- Identical tool paragraphs/facts become ID references to their fully retained initial context. Only byte-identical JSON entries are deduplicated; new or changed entries remain in the result. Optional evidence/metric actions and bounded continuation remain available.
- Request provider SSE and consume it server-side. Record headers/first event/first answer-text/completion timings, output character counts, request bytes, call index and whitelisted reasoning/cache usage. No streamed draft text or private reasoning appears in default logs or the browser. Only a completed response reaches the unchanged verifier.
- A truncated/incomplete/error stream never becomes a checked answer. Abort, Stop, resource bounds, call IDs and encrypted reasoning continuity remain enforced.

Model remains `gpt-6.1-sol`, effort low, schema `v2-brief-schema-2`, output ceiling 8,192, at most two provider requests, one optional tool round/two tools. Keep the 120s last-resort deadline rather than extending it. No fallback provider, automatic retry, new sources or cache of arbitrary user questions.

## Interpretation and next gates

Two successful E1 trials are promising, not a latency distribution or proof that the prompt caused the whole improvement. Target 20–40s for this bounded task; measure median/tail latency, checked completion rate and total analyst review time across E1–E5, contextual follow-ups and tool-needed paths before adopting a service guarantee. Provider acceptance in under a second and first text under three seconds are diagnostic timings, not user-visible findings: the browser intentionally waits for checks.

The CLI answer preserves operating leverage, cash-conversion counterevidence, production-ramp limits and unanswered durability criteria. A semantic spot-check still finds citation completeness needing review: the qualitative finding combines execution, outlook and conditional financing, but its attached excerpts do not individually substantiate every material clause. A mechanical pass is not a semantic pass. Do not declare quality/pilot gates met; the next quality change should require claim-complete citations or omit unsupported extra clauses, then compare the same cases without trading away full evidence.

Official guidance: [latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization) recommends fewer requests and shorter generated output; input reduction alone usually has smaller benefits. [Streaming Responses](https://developers.openai.com/api/docs/guides/streaming-responses) provides typed lifecycle/text events. Here streaming improves diagnostics; it does not itself promise faster checked completion.
